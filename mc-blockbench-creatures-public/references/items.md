# 物品道具模：武器、法器、卡牌与显示效果

先按用途与实际格式选管线。物品道具是创作类型，不等于 Java 静态物品格式。

| 实际资产 | 使用本文件的范围 | 动作/导出依据 |
| --- | --- | --- |
| 独立 Java 物品、法器 | 道具设计及下文 Java 流程 | display、模型 JSON、纹理与 mcmeta |
| 嵌在角色中的剑、枪、牌或骨骼道具 | 道具设计；动态纹理部分按实际能力选用 | 原工程骨骼与动画导出，另读 [animation.md](animation.md) |
| 同时作为持有物和独立实体 | 分别声明两种资产用途 | 各自验证，不能默认共用同一导出 |

## 道具设计：先可辨认，再装饰

武器先从正常观察距离看出刀、剑、枪的轮廓，再调材质与装饰。枪头需有清楚的尖端、刃面、过渡和枪杆，不能只做细锥；黑金武器也要用明度区分枪刃、杆和饰件，避免整件黑成一团。装饰华丽程度由角色设定决定，不默认所有武器都素或繁。与人物一起检查长度、粗细、握柄位置、手的大小及持握角度；单/双手与剑鞘绑定见 [humanoids.md](humanoids.md)。

卡牌、符印等层叠道具先明确“文字层、承托层、透明主体、边框”的分工。文字用可读的贴图/面，不默认把字拆成密集 cube；若要求文字夹在透明实体中，需有真实底层与连贯厚度。边框连接、透明层侧视、双面重影、分层闪烁和展开前后轮廓都要检查。骨骼展开应是结构有序开合，不能变成碎片散落或整牌无限放大。

角色内的牌离手后如由独立实体接管，交接帧需匹配世界位置、朝向、比例和可见性；模型隐藏与粒子汇聚、附魔/攻击时刻交给代码契约。当前五行牌颜色、展开时序等属于项目设计，不是所有法器的默认。

以下各节针对 **Java 物品**。骨骼道具不照搬 display、mcmeta 或静态格式限制；方块/其他平台也先核对实际导出链。

## 可编辑层叠饰件

对于用户要反复复制、缩放的甲片或包饰，把一件组件的正反面、边缘和封边放进同一组；左右组件分别分组，内外层可设子组。保持组旋转为零并核对世界几何不变，避免分组时带动用户已定结构。

调整层数时分别列出总长、正面宽度、前后厚度、单片轮廓和相邻覆盖量。“新增一层、均分变小”应先固定总包络再重排覆盖，不等于延长整段或拉开层距。最后以用户保存版本为准，不再重跑旧生成器覆盖手改。不把特定比例或微错层值定为通用规则。

## 先建立资产清单

读取 model_format、版本提示、元素、分组、UV、纹理源和 display。记录目标 Minecraft 版本、加载器/模组、导出器、资源路径；文件里的 `java_block_version` 只是格式信息，不能直接当成用户实际运行的游戏版本。沿用项目约束，不凭最新版本常识修改旧项目。

按功能列出主体、内壁、装饰、火焰、云雾、符文、粒子等已有层。区分实际面、透明卡片、体积块；对每一动态层记录：

`所属组 → 元素/面 → 纹理索引或 UUID → UV/单帧范围 → 播放顺序/时长 → 导出资源 → 运行时能力`。

BBModel 内纹理通常可用列表索引引用；导出 JSON 的 `#key` 属于另一映射。先确认格式再解析，不把数字字符串、texture.id、UUID 与列表索引混为一谈。合并纹理或调整列表后更新引用，保留用户资产身份。

## 根据变化选择实现

| 需求 | 首选检查/实现 | 必须说明的边界 |
| --- | --- | --- |
| 平面火焰、星点闪烁、平面太极转动 | 低分辨率序列贴图；复用少量合理朝向的面 | 图像运动不等于真实几何运动；检查背面、侧面与循环 |
| 真实云块漂移或有厚度的结构转动 | 已有模组渲染器或项目动画管线 | 普通静态物品 JSON 不会自动执行骨骼动画；不要擅自改格式 |
| 静态格式中已有“多姿态几何＋透明帧轮换” | 先保留并理解其显隐时序，必要时局部修复 | 可造成元素和材质急剧增长；有明确约束才继续采用 |
| 原版风格星点/闪电粒子 | 能接入时用运行时粒子；纯资产交付可提供视觉替代 | 贴在物品上的面不是独立粒子系统，也不会自动 billboard |

先做一个能播放的效果，再扩展。序列贴图优先考虑图形变化；不要为了简单纹理闪烁复制整个模型的每一帧。需要真实空间运动却受静态格式限制时，说明可选实现和代价，不用“已实现动画”掩盖降级。

## 纹理动画

确认实际 PNG 尺寸、单帧尺寸和布局，不只信纹理元数据。竖条且帧为正方形时可用 `frame_count=height/width`；只有确认布局后才能这样算。矩形帧或图集需显式帧尺寸，不能自动切成正方形。

核对 `frame_time`、`frame_order_type`、`frame_order`、`frame_interpolate` 以及 PNG 帧内容。检查至少起点、1/4、1/2、3/4 和循环接缝；对于短闪光和稀疏自定义帧序，额外检查全部实际显隐切换，不能只等距抽样。名为“animated/20fps”不是播放证明，全部重复帧也不构成可见运动。

在项目的 Java 纹理导出流程中核查 PNG 对应的 `.png.mcmeta`：animation、frametime、frames（含重复索引或单帧时长）、interpolate 必须与预期一致；有其它控制器则验证该控制器。`frametime` 以游戏 tick 计，不是毫秒；不要把 fps 数字原样当成 frametime。像素效果通常关闭帧间混色，但尊重明确要求。

BBModel 纹理设置不等于外部 `.mcmeta` 已存在或已正确导出。交付仅有 BBModel 时，明确编辑器内已检查的范围以及运行时所缺的资源。不得因为 `animations` 数量为 0 报告“没有动画”；分开报告骨骼动画和纹理动画。

## 显示与渲染能力

- 检查 GUI、地面、展示框、第一/第三人称、左右手 display 中实际使用的槽位；保留原缩放约定，检查特效被裁切、遮手、中心偏移和背面消失。
- 别把关掉 AO、`shade:false`、亮黄色贴图等同于自发光。区分颜色亮、环境暗处仍亮、bloom、照亮周围四件事。`light_emission`、emissive/fullbright、透明混合的支持随版本和渲染器而变，按当前项目代码或官方文档核实并实测。
- 半透明 PNG 不保证物品渲染层正确混合；检查 alpha test/blend、深度写入、透明排序、视角变化和多层叠加变黑。能力不足时说明并提供用户能评估的替代，不能静默改成不透明。
- 旋转角、范围、元素上限等格式约束以目标版本及实际导出器为准。不要借自由模型预览宣称能按原样导出为 Java 物品。

## 物品验收与交付

用 `python scripts/audit_item_bbmodel.py model.bbmodel --report report.json` 生成只读结构报告。可用 Pillow 时额外解码嵌入 PNG 检查 alpha 和帧内容；`--pixels` 开启，缺依赖会明确报错。它不会评价模型是否漂亮、证明真实发光或代替游戏渲染。

然后查看实际模型多角度、GUI 与手持尺寸，以及完整动态循环。针对用户指出的问题逐条记录“已改什么、证据是什么、哪些仍待运行时验证”。输出可编辑 BBModel；任务要求可直接入游戏时同时交付导出的模型、纹理、动画元数据及必要接入代码。仅修改 skill 的任务不要顺带重做用户模型。

物品特效制作读 [item-effects.md](item-effects.md)。
